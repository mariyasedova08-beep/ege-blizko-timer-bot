# Отдельный тестовый HTTPS — подготовка 02.11.2026

Планируемый адрес: https://lab-test.77-233-212-200.sslip.io/lab-app. До выполнения установщика и независимой внешней проверки этот адрес не считается готовым.

Подтверждено владельцем через Timeweb-консоль: nginx и certbot установлены, nginx -T успешен, новый адрес разрешается в 77.233.212.200, рабочие сайты используют другие имена. В nginx подключены /etc/nginx/conf.d/*.conf и /etc/nginx/sites-enabled/*.

## Что делает установщик

- Проверяет DNS, ожидаемый sandbox на loopback 8768 и исходную конфигурацию nginx.
- Создаёт только /etc/nginx/conf.d/ege-lab-sandbox-test.conf с точным новым server_name; рабочие конфиги не редактируются.
- Сохраняет предыдущий тестовый конфиг и сертификатный hook, SHA-256 всех остальных загруженных конфигов, HTTP-статусы и отпечатки сертификатов трёх рабочих сайтов.
- Выпускает отдельный сертификат ege-lab-sandbox-test через certbot certonly --webroot. Используется единственная существующая учётная запись production CA; новые аккаунты не регистрируются, новые условия обслуживания автоматически не принимаются. Если подходящего аккаунта нет или их несколько — остановка до изменения nginx.
- Использует отдельный пустой certbot.ini, отдельные рабочую/логовую папки и --no-directory-hooks; не запускает глобальные directory hooks и не использует --nginx/--standalone.
- Перед каждым reload проверяет неизменность рабочих файлов и nginx -t. Выполняется мягкий reload nginx, без stop/restart; бот, базы, sandbox-сервис и другие приложения не перезапускаются.
- Включает TLS только для нового имени и проксирует его в 127.0.0.1:8768. Проверяет сертификат обычной TLS-валидацией, SHA HTML, ожидаемую сборку и API химии.
- Повторно проверяет рабочие сайты. При ошибке восстанавливает только прежний тестовый конфиг/hook и выполняет проверенный reload. Новый сертификат не удаляется и не отзывается; новая renewal-конфигурация при откате убирается в резервную копию, чтобы не оставить ненужное автоматическое продление.

Добавленные пути:

- /var/lib/ege-lab-test-https — состояние установщика, резервные копии, webroot, рабочие файлы и логи.
- /etc/nginx/conf.d/ege-lab-sandbox-test.conf — только новый сайт.
- /usr/local/libexec/ege-lab-test-tls-reload — deploy-hook только для точного нового certificate lineage.
- /etc/letsencrypt/live/ege-lab-sandbox-test и соответствующие archive/renewal — новый сертификат.

У существующего диагностического SSH-пользователя не появляются права записи или новые sudo-команды. Начальная установка выполняется владельцем в доверенной root-консоли. После этого внешняя проверка запускается через GitHub без секретов и без SSH.

## Откат

```bash
python3 /var/lib/ege-lab-test-https/installer.py --rollback
```

Возвращает последнюю сохранённую конфигурацию только тестового сайта и hook. Рабочие сайты дополнительно проверяются на неизменность. Ключи/сертификаты рабочих сайтов не читаются для копирования, не заменяются и не отзываются.

## Проверки и ограничения

Локально проходят 8 новых проверок: точный новый hostname, отдельный challenge webroot, ограниченные флаги Certbot, сохранность остальных конфигов, безопасное удаление только своего нового конфига при откате, сохранение выданного сертификата, отказ неизвестному конфигу и неверной HTTPS-сборке, обнаружение изменения сертификата рабочего сайта. Ещё одна проверка запускает nginx -t с обоими сгенерированными конфигами и временным самоподписанным сертификатом и свободными непривилегированными портами, только в одноразовом GitHub runner с установленным nginx. Настоящий сертификат в CI не запрашивается.

Сам выпуск сертификата на Timeweb, публичная доступность имени и проверка через физический iPad/Safari ещё впереди. Let’s Encrypt может отклонить запрос из-за общих лимитов sslip.io либо сетевой недоступности HTTP-01; установщик в таком случае откатывает новый сайт. Не следует отключать проверку TLS или выдавать HTTP за готовый HTTPS.
