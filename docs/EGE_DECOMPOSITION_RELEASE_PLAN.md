## Что уже подготовлено

`deploy/ege-decomposition-readonly-preflight.py` проверяет код без исполнения и **без записей на VPS**: наличие одного `main()`, точное положение единственного проверенного места вставки, отсутствие установленного тренажёра, наличие `run_bot_live85.py` и обоих кандидатов, отсутствие симлинков и корректный Python AST. Выдаёт только хеши файлов, не текст серверного кода. Совпадение структуры исходников Github и сервера **не предполагается**. Проверяющий скрипт принципиально **не изменяет существующие файлы**.

Его `check(live_dir, candidate_dir)` допускается применять к отдельным **локальным копиям** или в защищённой среде после подготовки неизменных кандидатов. Положительный результат означает *совместимость точки вставки*, но не полноценную совместимость приложения.

## Что необходимо до разрешения настоящего выпуска

- На VPS только для чтения выяснить **текущие** SHA-256 серверного `run_bot_production.py` и оба целевых имени (отсутствуют или существуют). Любое неожиданное состояние — STOP. Сервер мог измениться после предыдущих аудитов.
- Проверить защищённой процедурой, что серверный `run_bot_live85.py` предоставляет необходимые функции. Никакого прямого импорта модулей рабочего бота в preflight: импорты некоторых модулей имеют побочные действия.
- Отдельно согласовать **ограниченный root-owned release-helper** и SSH forced-command для этого **одного выпуска**. Не расширять разрешения существующих лабораторных helper или открывать произвольный SSH shell.
- Проверить SHA-256 каждого кандидата из **неизменяемого GitHub-коммита** PR #82 и создать отдельную staging-директорию с запретом доступа ученикам.
- До любых изменений на сервере сохранить **согласованную резервную копию** реальных `run_bot_production.py`, конфигурации сервиса, двух целевых имён (если есть), и SQLite-баз из `/opt/bots/ege-blizko/data` через SQLite backup API; для каждого `PRAGMA integrity_check=ok`. Хранить резервную копию отдельно, с ограниченными правами; не публиковать её в GitHub или чат.
- Захватить существующую блокировку автообновлений и сверить hash/server revision **внутри блокировки**; никакого `git pull`, `reset`, `checkout`, очистки репозитория.
- Подготовить новое содержимое `run_bot_production.py` **в памяти/временном каталоге**, проверить его AST и единственность вставки, после чего выполнить атомарную установку с сохранением владельца/прав. Если попытка установки не проходит — никаких перезапусков.
- Перед публикацией обязательно отдельное одобрение владельца; после одобрения — точечный рестарт только `ege-blizko.service`, проверка статуса **и** HTTP `/health`, реальный запуск новой команды и тестовый ответ на вопрос.
- На ошибке — откат новых двух модулей и прежнего серверного `run_bot_production.py`, повторная проверка `/health`. **Не откатывать/не переписывать всю БД автоматически**: новые таблицы безопаснее оставить до отдельного согласованного удаления, не затрагивая другие записи.

## Конкретные ограничения на текущий момент

1. Публичная ветка `main` **не является** актуальной полной production-копией; все существующие серверные исправления нужно сохранить.
2. Read-only preflight **ещё не выполнен против последней версии VPS**. Тесты на искусственных образцах не заменяют проверку текущего сервера.
3. Фактический root-owned helper для **записи** на VPS в рамках этого PR не устанавливался и релиз не запускался.
4. Исходники VPS, ученические данные, SSH-ключи, токены, резервные копии и внутренние пути с секретами **никогда не помещать в открытый GitHub**.
