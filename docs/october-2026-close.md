# Октябрь: итоги 5 ноября, условия 27 октября в 19:00 МСК

Владелец явно разрешил применить перенос и запланировать сообщения в чат 11 класса
и каждому ученику. Повторного согласия на публикацию этого объёма не требуется.

## Даты и аудитория

- Уведомление: 27.10.2026 19:00 Europe/Moscow, один раз в учебный чат/тему и
  каждому из 13 связанных Telegram-аккаунтов курса `6a8c4641d6c9f299cf1387a6`.

  80%+, три завершённые тренировки по каждой назначенной теме, октябрьские пробники

  Верхняя граница исключающая: 05.11.2026 00:00+03:00. Она относится к действиям
  учеников. Пробник относится к месяцу по дате проведения, поэтому оценку за
  31 октября можно внести в ноябре.
- Автоматическое закрытие октября и предложение выбрать «Прорыв»: с 05.11.2026
  09:00 МСК, сохранён прежний час закрытия. До этой даты запрещены автоматическая

  этот день, закрытие догоняется в течение ноября, без повторных доставок.
- Если ни одного результата пробника 31.10 ещё нет в БД, автоматическое закрытие
  ждёт его внесения. Система не может определить, закончена ли проверка всех работ:
  наличие хотя бы одной оценки разрешает расчёт; ученики без результата пока не
  проходят условие пробника. Перед 5 ноября преподаватель должен завершить импорт.
- Розыгрыш остаётся ручным в существующем кабинете после проверки данных, с 5 ноября.
  Никакой случайный выбор без нажатия владельцем не запускается.
- Срок оплаты ноября остаётся 07.11.2026 включительно; платёжный код не меняется.

## Расчёт

Показатель своевременности обычного ДЗ не переписывается. Поздняя сдача закрывает
долг для допуска к скидке, но не становится «сдано вовремя». Расчёт баллов и индекса
«Ученик месяца» сохраняет существующие месячные правила; новое окно дополняет
только проверку допуска к скидке. Для итоговых ДЗ используется октябрьский набор
работ, подтверждённый октябрьскими сдачами; улучшение до 80% в окне допуска считается,
но ноябрьская новая работа не добавляется. Для тренажёров используется существующий
октябрьский набор назначенных тем; дополнительные попытки 1–4 ноября учитываются
только внутри истории назначения. Разложение не становится обязательным.

Сентябрь, ноябрь и остальные месяцы сохраняют прежний календарь/расчёт.
Новые обёртки установлены поверх `month_payload`, поэтому более поздний адаптер
истории назначений не может затереть октябрьскую проверку допуска.

## Доставка

Очередь создаёт installer, с enabled=0 до готовности файлов. В ней один course и
13 student, без имён/Telegram ID в репозитории и логах. Telegram ID берутся из БД.
При отправке повторно проверяются активность и курс ученика, тип чата и членство.
Чат ОГЭ исключён. Тема курса сохраняется. Новые участники не добавляются молча.

Отправка идёт через существующий 30-секундный тик бота. Это расписание Telegram,
не напоминание ChatGPT. Время отправки — первый тик с 19:00, в пределах суток 27.10;
после полуночи просроченное объявление автоматически не отправляется.

PK campaign/kind/recipient и транзакция pending → sending обеспечивают отсутствие
дублей при повторе/перезапуске. sent хранит message_id. При неопределённой сетевой
ошибке статус uncertain; автоматического повтора нет, чтобы не повторить сообщение,
которое Telegram мог принять. После сбоя процесса sending также требует ручной
проверки. Forbidden/BadRequest → failed. Бывшие активные ученики исключаются.
Итог доставки необходимо проверить после назначенного времени; сейчас 14 — это
размер очереди, не подтверждение отправки.

## Выпуск и откат

Два разрешённых runtime-файла: точечная AST-правка `kulek_rewards.py` и новый
`october_2026_close.py`. Entry point, лаборатория, ПРЕПАДМИН, платежи не меняются.
Полный приватный VPS-код в GitHub не копируется. Installer содержит проверяемые
копии нового модуля и преобразователя, их равенство проверяется тестом.

Поддерживаются только две проверенные версии kulek_rewards:
- VPS после разложения: 76ab3666a6b62488f15b266dd6de2e4eeff4ec1635a84abb3cf7d8dd0b3f55a3
  → 2651b2512996ed9592fa8d4c109453b6857847496648a2db157839716b172a3d;
- текущая публичная версия dd4c39bdbc064d098e262e5fadffdff7dbf07646e437c39724bb1ea6d872598e
  → 868ad0ea360d104be302db5b0d32f903867f659a7140708386d26b9d7c2ac3f9.

Перед записью проверяются версия, активный ege-blizko под ege-bot, точный путь БД,
CHAT_ID, 13 уникальных учеников нужного курса и наличие истории назначений.
Backup: исходный файл с uid/gid/mode, online SQLite backup с integrity_check,
каталог `/var/lib/ege-october-close-20261026` mode 0700, копии 0600.
Миграция только additive: october_2026_config и october_2026_deliveries.
Общий lock выпуска, atomic+fsync, сохранение владельцев и прав, проверка sidecar
прав SQLite, restart только ege-blizko, active + /health + marker startup + 14 pending.

Одноразовый bootstrap по точному SHA устанавливает root-owned helper и sudoers
только с install/rollback для этого RELEASE. Не расширяет authorized_keys,
не изменяет бот и не запускает рассылку. Workflow запускается вручную в main,
operation=install и требует существующую защищённую среду ege-lab-production.
Push/merge не деплоит. Dispatch/approval отсутствуют в подключённых инструментах:
владелец запускает их в интерфейсе GitHub.

Успех публикации:
`OCTOBER_CLOSE_RELEASE_OK_BACKUP_HEALTH_AND_14_MESSAGES_SCHEDULED`.
Установить до 27 октября 18:55 МСК; позднее требуется пересмотр плана, не молчаливый
перенос времени. До этого маркера расписание на VPS не считается применённым.

Сбой записи/health → автооткат файлов и отключение собственной очереди.
Ручной rollback через тот же workflow восстанавливает файл и права, убирает новый
модуль, выключает собственную очередь, перезапускает и проверяет health.
База из старой копии НИКОГДА не восстанавливается: новые оплаты/ответы сохраняются.
Pending становятся cancelled; уже отправленные сообщения/журнал не удаляются.
Ручной откат 1–5 ноября до 09:00 блокируется, потому что исходный код мог бы
объявить октябрь досрочно. В этот период нужен forward fix с сохранением запрета.

## Проверенный повтор после отката (26 октября)

Первый выпуск Actions 40361761127 остановлен с HEALTH_OR_STARTUP_MARKER_MISSING,
автооткат подтверждён. Пользовательский read-only вывод показал, что startup marker
October 2026 и Kulek rewards ready действительно были в журнале. Точный первичный
фактор (HTTP readiness/тайминг/выбор журнала) не установлен; отсутствие traceback
не доказывает отсутствия ошибки. Нельзя объявлять старый выпуск успешным.

Новая проверка не использует локальную строку --since: выбирает журнал текущего
_SYSTEMD_INVOCATION_ID, требует оба startup marker, HTTP 200 и active, причём два
успешных наблюдения подряд в одной invocation. Новый предел ожидания 120 секунд.
ConnectionResetError при запуске допускает повтор проверки, но не отменяет ни одно
условие. При таймауте выводятся только безопасные поля active/http/marker/journal.
Логи приложения не публикуются. Выпуск печатает SHA256 исполняемого root-helper,
поэтому его версию можно сопоставить с закреплённой bootstrap-копией даже при
повторе старого release-job, который лишь вызывает установленную root-команду.

Повтор существующей установки разрешён только при доказанном полном откате:
root-only backup-каталог, original.py побайтно равен текущему исходному файлу,
метаданные uid/gid/mode совпадают, первая SQLite-копия проходит integrity_check,
конфигурация очереди точно совпадает и выключена, все 14 правильных получателей
имеют cancelled и message_id=NULL. Sent/sending/uncertain/failed или иная настройка
запрещают повтор без разбора. Первая резервная копия никогда не перезаписывается.
Перед повтором дополнительно создаётся retry-<time_ns>-database.sqlite, затем
реактивируются только те же 14 отменённых записей. Восстановления БД нет.

Bootstrap может заменить helper только с исходного закреплённого SHA256
`d9d118cb22ab2f08138223355825fc43078f8e08e8d14bf49c1cdcdf723a15e8`
на новую проверенную копию либо подтвердить уже установленную новую копию.
Неизвестный helper отклоняется. Sudoers, SSH-ограничения и runtime при bootstrap
не расширяются/не меняются. Уже данное поручение применить перенос включает этот
ремонт выпуска; новое согласие на тот же объём не требуется.

Добавлены 7 тестов (всего 35): полный retry после rollback с сохранением первой
копии и новых оплат; запрет sent/ambiguous очередей; запрет изменённых backup/config;
текущая invocation и две стабильные проверки; отсутствие marker не проходит;
transient ConnectionResetError; перезапуск сбрасывает счётчик стабильности.
