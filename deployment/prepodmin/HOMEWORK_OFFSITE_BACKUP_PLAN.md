# ПРЕПОДМИН — подготовка внешнего резервного копирования письменных ДЗ

**Статус: план, не установлен.** Ни одна команда из этого документа
не запускается автоматически. Согласование владельца отдельно для:
(1) выбора облачного хранилища; (2) создания учётных данных/папок;
(3) теста восстановления; (4) публикации новой функции.

## Исходная ситуация

- Работающая SQLite: /opt/bots/prepodmin/data/teacher_product.sqlite3.
- Ежедневная локальная резервная копия БД: root-owned
  /var/backups/prepodmin/daily (наличие и статус проверить на сервере).
- Для письменных ДЗ запланированы файлы вне Git:
  /opt/bots/prepodmin/data/homework_uploads, приватный 0700.
- Локальные копии БД НЕ защищают файлы, а данные в пределах одного VPS
  могут пропасть одновременно. Никаких offsite/restore гарантий пока нет.
- Нельзя изменять текущий backup-таймер и ЕГЭ БЛИЗКО.

## Рекомендуемая независимая схема

1. Отдельное S3-совместимое хранилище вне VPS (выбор провайдера и
   отдельного ключа доступа — после согласования). Права ключа ограничить
   исключительно бакетом ПРЕПОДМИНА. Не складывать ключи в Git/чат.
2. Передавать данные по HTTPS программой restic, шифрующей архивы
   до отправки. Ключ дешифрования держать также вне VPS, в двух
   защищённых местах. Сервисную запись и ключ отделить от ЕГЭ БЛИЗКО.
3. В начале каждой сессии делать **online snapshot SQLite** в root-owned
   временную директорию через deployment/prepodmin/sqlite_snapshot.py;
   проверить PRAGMA integrity_check=ok. Простое копирование живой БД
   через cp небезопасно при SQLite WAL.
4. Затем передать В ОДИН restic snapshot: проверенный снимок SQLite и
   неизменяемые файлы всех попыток из приватного каталога. Порядок важен:
   сперва SQLite, потом файлы. При текущей модели файлы появляются до
   фиксации строки в БД и не изменяются; это позволяет захватить файлы,
   на которые ссылается снимок базы. Данные нового ученика после момента
   SQLite-snapshot не гарантируются до следующего цикла.
5. Не удалять предыдущие файлы до завершения политики хранения и
   теста восстановления. Не менять исходные папки и локальные backups.
6. Запустить отдельный systemd timer root-owned (например ежедневно
   ранним утром с пропущенным запуском после включения VPS).
   Должно быть явное уведомление о сбое или устаревшей последней копии.
   Контроль локального места, S3-квот и стоимости отдельно.
7. Регулярно восстанавливать тестовую копию в изолированный каталог,
   НЕ поверх рабочей БД/учеников. Проверять SQLite integrity, количество
   и SHA256 вложений, что все ссылки на сохранённые файлы разрешаются,
   и что восстанавливаются замечания/попытки. Не начинать выпуск
   без успешного полного пробного восстановления.
8. Хранить только минимально необходимый срок, согласованный для
   детских письменных работ. Логи не должны содержать полные URL файлов
   с токенами, ключи, личные имена или содержимое решений.

## Диагностика ДО какой-либо настройки

Запустить read-only аудит deployment/prepodmin/audit_homework_readonly.sh
через доверенный обычный root SSH, а не через существующий ограниченный
GitHub-ключ PREPODMIN. Ключ GitHub связан с принудительной командой
prepodmin-release, не предоставляет shell и использовать его для
проверок не следует.

Скрипт выводит только маркеры OK / NOT_CONFIRMED; он не может
подтвердить наличие удалённой зашифрованной копии или успешный restore.
Если каталог и новые Nginx locations ещё отсутствуют, это ожидаемый
NOT_CONFIRMED и не повод устанавливать их без отдельного согласия.

## Осталось определить

- Провайдер отдельного S3-совместимого хранилища и максимальный бюджет.
- Политика хранения и удаления детских работ.
- Кто хранит ключ восстановления и подтверждает восстановление.
- Периодичность offsite, например ежедневно; желаемая потеря
  максимум одного дня при аварии.

**Не активировать TEACHER_PRODUCT_HOMEWORK_UPLOADS_ENABLED до полного
backup/restore, Nginx, приватности и ручных HTTPS-проверок.**
