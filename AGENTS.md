# Правила работы ИИ-разработчика

Этот репозиторий обслуживает несколько **разных** продуктов. Задача ИИ — самостоятельно разрабатывать, проверять и готовить изменения, а не перекладывать кодирование, ZIP/SCP/SSH и диагностику на владельца продукта.

## Продукты и границы
- **ЕГЭ БЛИЗКО (Telegram)** — действующий образовательный бот, тренажёры, домашние задания, уведомления, статистика и Кулёчки.
- **Лаборатория ЕГЭ БЛИЗКО** — самостоятельный модуль; выпускается отдельно от остального бота.
- **ПРЕПОДМИН** — отдельный продукт со своей системой выпуска; нельзя смешивать его изменения с ЕГЭ БЛИЗКО.
- **Платформа ЕГЭ БЛИЗКО** — отдельная LMS, не равна Telegram-боту.
- Личный медицинский бот и другие приложения НЕ входят в разрешённый объём работ.

## Обязательный процесс для каждого изменения
1. Выяснить целевой продукт, текущую ветку, действующий способ запуска и границы изменений.
2. Читать фактический код GitHub и **отдельно** сверять отличия с production, если они существенны. Не предполагать, что ветка GitHub соответствует состоянию сервера.
3. Создать отдельную feature-ветку; не писать непосредственно в main и не удалять незакоммиченные изменения на сервере.
4. Сделать код, тесты, миграции и инструкции отката. Проверить синтаксис и поведение важных сценариев, включая повторные нажатия, отсутствие дублей и граничные случаи.
5. Открыть PR с ясным описанием: что изменилось, что проверено, какие риски и что будет **только после** публикации.
6. До отдельного согласия владельца разрешены лишь read-only проверки и подготовка к выпуску. Согласие на разработку НЕ является согласием на публикацию.
7. Выпуск: строго определённый SHA и разрешённые файлы, сверка совместимости с production, резервная копия, сохранение владельца/прав, точечное обновление, проверка health/logs, готовый откат. Ни автоматического deploy по push/merge, ни массовой замены проекта.
8. После выпуска проверить реальные сценарии, не объявлять об успехе только по `active`.

## Важные инварианты
- Не выполнять `git pull`, `git reset --hard`, `git checkout` поверх живого VPS-проекта; там есть локальные изменения, отсутствующие в GitHub.
- Не переписывать базу данных, аккаунты, оплаты, чеки, прогресс, ДЗ, результаты тренировок, Кулёчков и историю наград без отдельной согласованной миграции.
- Общедоступный тренажёр не должен автоматически становиться обязательным в 11 классе.
- Изменение лаборатории не должно незаметно менять Telegram-бот или ПРЕПОДМИН.
- Команды PowerShell и SSH владельцу — крайний случай для **одноразовой настройки доступа**, когда нет безопасного подключённого инструмента; не стандартный процесс разработки.
- Не просить пароли, токены, приватные SSH-ключи или скриншоты с секретами в чате. Секреты должны храниться только в защищённых настройках GitHub.
- Любой workflow с SSH/deploy требует проверки доверенного хоста, ограниченной учётной записи, отдельных разрешений и ручного подтверждения среды.
- Не обещать фоновую работу или публикацию без фактически запущенных механизмов.

## Что считается готовым
**Разработка готова:** код и тесты в PR, результаты проверок доступны, production не тронут.
**Публикация готова:** отдельное подтверждение, реальный успешный запуск, контроль работоспособности и возможность отката.
**Если нет полного безопасного доступа:** назвать конкретный одноразовый шаг подключения, а не давать регулярные SSH-команды.
